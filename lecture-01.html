Information & Data Representation

How a machine that only knows 0 and 1 comes to hold numbers, negative numbers, and every letter of every language — shown as animations, not just described.

§1 · A bit — the atom of information

Every file, image and message is built from one thing: a choice between two options.

A bit (binary digit) is the smallest unit of information: it answers a single yes/no, on/off, 0/1 question. Claude Shannon defined the information in an event of probability p as −log₂(p) bits. One fair coin flip (p = ½) carries exactly 1 bit. Guessing a card's suit (1 of 4, p = ¼) carries 2 bits. Each time you double the number of equally-likely possibilities, you pay exactly one more bit.

💡 What to notice Watch the bit-count rise by 1 every time the options double — 2→1 bit, 4→2 bits, 8→3 bits, 256→8 bits. That "+1 per doubling" is the whole reason a single byte (8 bits) names exactly 2⁸ = 256 different values.

§2 · Decimal → Binary

The classic "repeated division by 2" — but watched, not just read.

To convert a decimal number to binary we divide by 2 again and again, keeping each remainder, and read the remainders from bottom to top. In a printed book this is a static block of text. Here, press Play and each division appears in turn, then the bits assemble into the answer.

§3.2 · One's Complement & Two's Complement

Two ways to write a negative number in bits — and why the second one won.

A computer never stores a written "−" sign. To hold a negative integer it stores a different bit pattern in the same fixed width and agrees on how to read it. Two schemes matter, and the second is built from the first.

One's complement negates a number by flipping every bit (0↔1, the bitwise NOT). It is simple, but it has two zeros — 0000 0000 (+0) and 1111 1111 (−0) — and adding numbers sometimes needs an extra "end-around carry" correction.

Two's complement takes the one's complement and adds 1. That single extra step removes the double zero and lets one adder circuit handle both addition and subtraction. Every modern CPU uses two's complement for signed integers.

The rule in one line: two's complement = one's complement + 1 = (flip all the bits) then (add 1).

Detailed worked example — represent −43 in 8 bits. Start from +43 and negate it. Watch the one's complement appear as the middle line, then the +1 turn it into the two's complement:

start   +43         0010 1011
one's complement: 1101 0100   ← flip every bit (0↔1)
add one:         +0000 0001
                  ─────────
two's complement: 1101 0101   = −43

Reading it back. The leftmost bit is the sign: 1 means negative. To decode 1101 0101, apply the very same "flip + 1" to get the magnitude: flip → 0010 1010, add 1 → 0010 1011 = 43. So the pattern is −43. Negation is its own inverse.

Why it matters — subtraction becomes addition. A CPU computes 43 − 26 as 43 + (−26), where −26 is just the two's complement of 26:

+26 = 0001 1010  →  two's complement (−26) = 1110 0110

   0010 1011   (+43)
 + 1110 0110   (−26)
 ───────────
 1 0001 0001   ← drop the carry out of 8 bits
   0001 0001   = +17  ✓
💡 What to notice One's complement is only the first half of the job — flipping the bits. The +1 is what turns it into two's complement, and that one extra step is the whole reason there is a single zero and one adder for both + and −. In the next panel, watch that flip-then-carry happen bit by bit.
Range (8-bit two's complement): −128 … +127 — one extra negative value because there is no wasted −0. For n bits: −2ⁿ⁻¹ … +2ⁿ⁻¹−1.

§3.3 · Two's Complement

"Flip all the bits, then add 1." Watch it happen to +43.

Every modern CPU stores negative integers in two's complement. To negate a number you invert every bit and add one. The carry that ripples through the "add 1" step is exactly what a still image cannot show — so here each bit flips, then the carry travels right-to-left.

Negate +43 → −43 (8-bit)

animated
💡 What to notice Follow the leftmost bit: it starts at 0 (positive) and ends at 1 (negative) — in two's complement that top bit is the sign. And notice the carry stops the moment it meets a 0; it does not always travel the whole width. That single rule lets the CPU subtract using the very same adder it uses to add.
✓ Check: 0010 1011 (+43) → flip → 1101 0100 → +1 → 1101 0101 = −43.

§4 · Real Numbers — IEEE 754 (32-bit)

How a fraction like 0.325 or a value like −6.625 becomes 32 bits.

Integers are not enough — we also need fractions. The IEEE 754 standard stores a real number in binary scientific notation:

value = (−1)S × 1.fraction × 2(E − 127)

A 32-bit single-precision number splits into three fields: 1 sign bit (0 = +, 1 = −), 8 exponent bits stored with a bias of 127 (so the real exponent is E − 127), and 23 mantissa bits — the fraction after an implicit leading 1. The recipe is always the same: sign → convert to binary → normalise to 1.xxx × 2ⁿ → biased exponent E = n + 127 → 23 mantissa bits → assemble.

Example A — convert 0.325. A fraction with no exact binary form, so it is stored to the nearest 23-bit value (this is why 0.325 is never held exactly).
Step 1 · Sign      0.325 ≥ 0  →  S = 0
Step 2 · Integer   0  →  0
Step 3 · Fraction multiply by 2, keep the integer digit each time:
          0.325×2 = 0.65 → 0
          0.65 ×2 = 1.30 → 1
          0.30 ×2 = 0.60 → 0
          0.60 ×2 = 1.20 → 1
          0.20 ×2 = 0.40 → 0
          0.40 ×2 = 0.80 → 0
          0.80 ×2 = 1.60 → 1
          0.60 ×2 = 1.20 → 1  … pattern 0011 repeats forever
          0.325 = 0.0101001100110011001100110011…₂
Step 4 · Combine  0.0101001100110011…₂
Step 5 · Normalise first 1 is 2 places right of the point:
          0.01010011…  →  1.0100110011001100110011…× 2⁻²   (n = −2)
Step 6 · Exponent E = n + 127 = −2 + 127 = 125 = 0111 1101₂
Step 7 · Mantissa 23 bits after the "1." (rounded):
          0100 1100 1100 1100 1100 110

Step 8 — assemble the 32-bit word:

exponent · 125

mantissa (23)
Result: 0 01111101 01001100110011001100110 = hex 0x3EA66666. Decoded back it is ≈ 0.32499999, not exactly 0.325 — the price of a repeating fraction.
Example B — convert −6.625. This one is exact: 0.625 = 0.101₂ terminates.
Step 1 · Sign      −6.625 < 0  →  S = 1, work with 6.625
Step 2 · Integer   6 = 110₂        (6→3 r0, 3→1 r1, 1→0 r1, read up)
Step 3 · Fraction 0.625×2 = 1.25 → 1
          0.25 ×2 = 0.50 → 0
          0.50 ×2 = 1.00 → 1  → stop (0)
          0.625 = 0.101₂
Step 4 · Combine  6.625 = 110.101₂
Step 5 · Normalise move the point 2 places left:
          110.101  →  1.10101 × 2²   (n = 2)
Step 6 · Exponent E = n + 127 = 2 + 127 = 129 = 1000 0001₂
Step 7 · Mantissa bits after "1." = 10101, padded to 23:
          1010 1000 0000 0000 0000 000

Step 8 — assemble the 32-bit word:

Result: 1 10000001 10101000000000000000000 = hex 0xC0D40000. Check: 1.10101₂ = 1.65625, × 2² = 6.625, sign negative → −6.625 exactly ✓.

animated
💡 What to notice Every step is exact — no rounding anywhere — because 0.625 terminates as 0.101₂. Follow the sign bit: it is decided first (1 = negative) but placed last, at the very left of the word. And watch the three coloured fields snap together in order — sign · exponent 129 · mantissa 10101000… — to give exactly 0xC0D40000.
💡 What to notice The two conversions run the identical eight steps; only the numbers differ. The real split is in Step 3: 0.625 terminates so −6.625 is stored perfectly, while 0.325 repeats and must be cut to 23 bits — which is exactly why 0.1 + 0.2 ≠ 0.3 in floating-point. And notice the bias: a small number (0.325) gives an exponent below 127, a larger one (6.625) gives an exponent above it.

§5.3 · UTF-8 Encoding

Pour the code-point bits into the byte template — literally.

Cyrillic А is code point U+0410 = 1040, which sits in the 2-byte range, so UTF-8 uses the template 110xxxxx 10xxxxxx. The eleven data bits are poured, left to right, into the x slots. Press play to watch each bit drop into place.

Encode «А» (U+0410)

animated
CODE-POINT BITS (11)
💡 What to notice The grey marker bits (110…, 10…) are never data — they only tell a reader "this byte starts a 2-byte character" or "this byte continues one." That self-describing frame is why UTF-8 can be read from any point in a stream, and why a Latin A still needs just one byte while Cyrillic needs two.
Result: 11010000 10010000 = bytes 0xD0 0x90. Latin A needs just one byte — this is why UTF-8 stayed compact for English while covering every script.

Chapter summary

🎬 You just covered

A bit is one yes/no choice; +1 bit per doubling. Division builds binary bottom-up. One's complement flips the bits; two's complement adds 1, giving one zero and one adder for + and −. IEEE 754 packs a real number into sign · biased exponent · 23-bit mantissa (0.325 repeats, −6.625 is exact). UTF-8 pours data bits into a self-describing byte frame.

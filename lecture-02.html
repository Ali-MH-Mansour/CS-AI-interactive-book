Computer Architecture

How a stored-program machine actually runs code — the fetch–decode–execute cycle, the memory hierarchy, and why a GPU trains neural networks so much faster than a CPU. Watched, not just described.

§1 · The Von Neumann model

One idea from 1945 that every computer you own still obeys.

In 1945 John Von Neumann described the stored-program computer: instructions and data live in the same memory and travel over the same wires. That single decision is why a computer is general-purpose — feed it different instructions and it becomes a different machine, with no rewiring. Every part hangs off a shared system bus.

CPU
Processor

Executes instructions. Holds the ALU (arithmetic + logic), the Control Unit (sequencing) and the registers.

Memory · RAM
Working memory

Holds the programs and data in use right now. Fast, but forgotten when power is cut.

System bus
The shared wires

Three channels: data (the values), address (which cell), control (read / write / clock).

ℹ︎ Key registers: PC = address of the next instruction · IR = the instruction being decoded · R1…R3 = general-purpose working registers. You will see all of these move in the animation below.

§2 · The fetch–decode–execute cycle

The three-beat rhythm every instruction dances, billions of times a second.

The CPU repeats three steps forever. Fetch: copy the instruction at address PC into IR, then advance PC. Decode: the Control Unit works out what the instruction means. Execute: the ALU (or a memory access) carries it out. A printed page can only list these steps. 💡 What to notice The PC ticks up by 1 during every fetch, before the instruction even runs — that is how the CPU always knows where to look next, and how a loop can later just set PC back. Also watch that only Execute changes data: fetch and decode move information around inside the CPU but compute nothing.

§3 · The memory hierarchy

Fast is small, big is slow — so the CPU searches from the top down.

There is no single memory that is both huge and instant, so computers stack several: tiny, blazing registers and cache next to the CPU; large, slow RAM and disk further out. When the CPU needs a value it looks in the nearest level first; if it is not there (a miss) it tries the next, paying more time at each step. Try a cache hit and then a cache miss and watch the total wait grow.

💡 What to notice A cache miss to RAM costs roughly 60× a hit — that jump is why fast code keeps the data it reuses close together (the principle of locality). The hierarchy is a bet: keep recently-used data near the top and most look-ups win at L1/L2 before ever paying the RAM price.

§4 · System software & the OS

The layer that stands between your program and the bare metal.

Your programs almost never touch the hardware directly. The operating system sits in between — it schedules which program runs, hands out memory, organises files, and talks to devices through drivers. At its core is the kernel, which alone runs in privileged mode; when your program needs the hardware it asks the kernel with a system call. That wall is what stops one buggy app from taking down the whole machine.

The stack, top to bottom: User applications → system utilities → Operating System (kernel) → device drivers / firmware → hardware. A system call is the doorway from the top half to the privileged bottom half.

§5 · Cloud computing

Renting computing over the Internet instead of owning it.

Cloud computing means using servers, storage and software on demand over the Internet. The three service levels differ by how much the provider manages for you:

IaaS
Infrastructure

Raw virtual machines, storage, networking. You install everything above it. Like renting a car. (AWS EC2)

PaaS
Platform

You upload code; the platform runs and scales it. Like taking a taxi. (App Engine, Heroku)

SaaS
Software

A ready-to-use application in the browser. Like riding the bus. (Gmail, Microsoft 365)

Behind it all: virtualisation — one physical server hosts many isolated virtual machines; containers (Docker) are a lighter version that share the host kernel, so they start in a fraction of the time.

§6 · CPU vs GPU — why AI needs the GPU

A few brilliant workers, or thousands of simple ones — race them.

A CPU has a few powerful cores tuned for complex, sequential work. A GPU has thousands of simple cores that all do the same operation at once. Training a neural network is millions of independent multiplications — exactly the job thousands of small cores devour in parallel. Press Play to send the same batch of 64 multiplications to both and watch them race.

💡 What to notice The GPU is not faster per core — its cores are actually slower. It wins by doing many at once. This only helps when the work splits into independent pieces (multiplications, pixels, matrix rows). Give a GPU one long sequential task and the CPU wins easily — which is why a real computer keeps both.

Chapter summary

🎬 You just watched

A stored program runs by fetch→decode→execute, with the PC always pointing one step ahead. Memory is a hierarchy the CPU searches top-down, and a miss to RAM costs ~60× a cache hit. A GPU beats a CPU on AI by doing thousands of independent multiplications at once.

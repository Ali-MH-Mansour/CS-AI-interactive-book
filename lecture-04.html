§1 · The Software Development Life Cycle§1 · دورة حياة تطوير البرمجيات

Software is not written in a single burst — it moves through six phases. Walk them, and watch the cost of a mistake climb.لا تُكتب البرمجيات دفعةً واحدة — بل تمرّ بستّ مراحل. سِر فيها، وشاهِد تكلفة الخطأ تتسلّق.

The Software Development Life Cycle (SDLC) is a structured framework that describes what work is done, in what order, and how quality is controlled from the first idea to the retirement of a system. The classic form has six phases: requirements analysis, design, implementation, testing, deployment, and maintenance. Press Step below to walk them one at a time — each phase shows the question it answers and the output it produces, while the bar tracks how expensive the same defect becomes the later it is caught.

دورة حياة تطوير البرمجيات (SDLC) إطارٌ منظّم يصف ما العمل الذي يُنجَز، وبأي ترتيب، وكيف تُضبط الجودة من الفكرة الأولى حتى إخراج النظام من الخدمة. وشكلها الكلاسيكي ستّ مراحل: تحليل المتطلبات، والتصميم، والتنفيذ، والاختبار، والنشر، والصيانة. اضغط خطوة أدناه لتسير فيها واحدةً تلو الأخرى — تُظهِر كلُّ مرحلةٍ السؤالَ الذي تجيب عنه والمُخرَجَ الذي تنتجه، بينما يتتبّع الشريط كم يزداد العيب نفسُه كلفةً كلّما اكتُشِف متأخّرًا.

💡 What to noticeما الذي نلاحظه؟ A defect introduced in requirements but not caught until production costs roughly 100× more to fix than if it were caught at the start — that steep climb in the bar is the single strongest argument for testing early and often. And notice the last phase: maintenance is not a footnote — 60–80% of a product's total cost is spent here, after the first release. The life cycle is mostly what happens after "done". العيب الذي يُدخَل في المتطلبات ولا يُكتشَف حتى الإنتاج يكلّف إصلاحه نحو 100 ضعف مقارنةً بلو اكتُشِف في البداية — وهذا التسلّق الحادّ في الشريط هو أقوى حجّةٍ للاختبار مبكرًا وباستمرار. ولاحِظ المرحلة الأخيرة: الصيانة ليست هامشًا — إذ يُنفَق 60–80% من كلفة المنتج كلِّها هنا، بعد الإصدار الأوّل. فدورة الحياة في معظمها ما يحدث بعد كلمة «انتهينا».

§2 · From source code to a running program§2 · من الشيفرة المصدرية إلى برنامجٍ يعمل

The CPU runs only machine code. Watch a Java file compile once, then run anywhere on a virtual machine.لا ينفّذ المعالج إلا شيفرة الآلة. شاهِد ملفَّ Java يُترجَم مرّةً، ثم يعمل في أي مكان على آلةٍ افتراضية.

Human-written source code must be translated before a CPU can run it. There are three models. A compiler translates the whole file to machine code ahead of time (C, Go) — fast, but tied to one platform. An interpreter executes the source line by line at run time (the Python shell, JavaScript) — portable, but slower. The hybrid model compiles once to platform-independent bytecode, which a virtual machine (VM) then runs (Java, C#, Python). Press Step and trace one Java program from .java all the way to the CPU.

يجب ترجمة الشيفرة المصدرية التي يكتبها الإنسان قبل أن ينفّذها المعالج. وهناك ثلاثة نماذج. يترجم المترجِم الملفَّ كاملًا إلى شيفرة آلةٍ مسبقًا (C، Go) — سريعٌ لكنه مرتبطٌ بمنصّةٍ واحدة. وينفّذ المفسِّر المصدرَ سطرًا بسطر وقت التشغيل (صدفة Python، JavaScript) — محمولٌ لكنه أبطأ. أمّا النموذج الهجين فيُترجم مرّةً إلى شيفرة وسيطة (Bytecode) مستقلّةٍ عن المنصّة، تشغّلها بعدها آلةٌ افتراضية (VM) (Java، C#، Python). اضغط خطوة وتتبّع برنامج Java واحدًا من .java حتى المعالج.

Trace: source → compile → bytecode → runتتبّع: مصدر ← ترجمة ← شيفرة وسيطة ← تشغيل

💡 What to noticeما الذي نلاحظه؟ The compiler runs once, producing hello.class — the same bytecode file runs unchanged on Windows, macOS or Linux, because the VM is the part that differs per platform. That is what "compile once, run anywhere" means. Contrast an interpreter, which re-translates every line every time it runs, and a pure compiler (C), whose .exe is fast but locked to one OS+CPU. The bytecode+VM model trades a little speed for portability. يعمل المترجِم مرّةً واحدة منتِجًا hello.class — وملفُّ الشيفرة الوسيطة نفسُه يعمل دون تغييرٍ على Windows أو macOS أو Linux، لأنّ الآلة الافتراضية هي الجزء الذي يختلف بحسب المنصّة. وهذا معنى «ترجِم مرّةً، شغّل في أي مكان». قارِن المفسِّر الذي يُعيد ترجمة كلّ سطرٍ في كلّ تشغيل، والمترجِم الصِّرف (C) الذي يكون ملفُّه .exe سريعًا لكنه مقيَّدٌ بنظام تشغيلٍ ومعالجٍ واحد. فنموذج الشيفرة الوسيطة + VM يقايض قليلًا من السرعة بقابلية النقل.

⚙︎ The full build pipeline (compiled C)خط أنابيب البناء الكامل (للغة C المُترجَمة): "Compilation" is really several stages: preprocess → compile → assemble → link → load → execute. Linking combines object files and pulls in library code (e.g. printf); loading is the OS placing the program in memory (Lecture 2's loader). «الترجمة» فعليًّا عدّة مراحل: معالجة مسبقة ← ترجمة ← تجميع ← ربط ← تحميل ← تنفيذ. الربط يدمج الملفات الكائنية ويُدرِج شيفرة المكتبات (مثل printf)؛ والتحميل هو وضع نظام التشغيل للبرنامج في الذاكرة (محمِّل المحاضرة 2).

§3 · Testing & debugging§3 · الاختبار وتنقيح الأخطاء

Testing shows a bug exists; debugging finds why. They are two different jobs.الاختبار يُظهِر أن الخطأ موجود؛ والتنقيح يجد لماذا. وهما وظيفتان مختلفتان.

Testing executes a program to find defects; debugging locates and fixes the cause of one that testing revealed. Testing is organised from the smallest unit of code up to the whole system.

الاختبار ينفّذ البرنامج ليجد العيوب؛ وتنقيح الأخطاء يحدّد سببه ويُصلحه بعد أن يكشفه الاختبار. ويُنظَّم الاختبار من أصغر وحدة شيفرة صعودًا حتى النظام كلِّه.
⚖︎ Dijkstra's principleمبدأ دايكسترا: "Testing can show the presence of bugs, but never their absence." Passing tests increases confidence; it never proves correctness. «الاختبار يمكن أن يُظهِر وجود الأخطاء، لكنه لا يُثبت غيابها أبدًا.» فاجتياز الاختبارات يزيد الثقة، لكنه لا يُثبت الصحّة.
Levels of testingمستويات الاختبار

🐞 A systematic debugging processعملية تنقيح منهجية: 1. Reproduce the exact input → 2. Localise where it happens → 3. Understand the root cause → 4. Fix the cause, not the symptom → 5. Verify with the full regression suite. Logic errors are the hardest: the program does not crash, it simply gives the wrong answer. 1. أعِد الإنتاج بالمدخل الدقيق ← 2. حدّد الموضع أين يحدث ← 3. افهم السبب الجذري ← 4. أصلِح السبب لا العَرَض ← 5. تحقّق بمجموعة اختبارات الانحدار كاملة. والأخطاء المنطقية هي الأصعب: لا يتعطّل البرنامج، بل ببساطة يعطي نتيجةً خاطئة.

§4 · Development methodologies§4 · منهجيات التطوير

A methodology decides how the SDLC phases are arranged in time — once, in cycles, or continuously.تحدّد المنهجية كيفية ترتيب مراحل دورة الحياة عبر الزمن — مرّةً، أو في دورات، أو باستمرار.

Waterfall runs the phases strictly in sequence — simple to manage, but a requirements mistake surfaces late and expensive. Iterative/Incremental builds the product in repeated cycles, each a small SDLC delivering a working increment. Agile (driven by the 2001 Manifesto) takes that further with short, adaptive cycles; its common frameworks are Scrum (fixed 2–4 week sprints) and Kanban (continuous flow, limited work-in-progress). DevOps extends Agile to operations through automation — CI builds and tests every change, CD releases it.

يشغّل الشلّال المراحلَ تسلسليًّا بصرامة — سهل الإدارة، لكن خطأ المتطلبات يظهر متأخّرًا ومكلفًا. ويبني التكراري/التزايدي المنتجَ في دوراتٍ متكرّرة، كلٌّ منها دورةُ حياةٍ صغيرة تُسلّم زيادةً عاملة. أمّا أجايل (بقيادة بيان 2001) فيمضي أبعد بدوراتٍ قصيرةٍ متكيّفة؛ وأشيع أُطره Scrum (سباقات ثابتة 2–4 أسابيع) وKanban (تدفّق مستمر، عملٌ جارٍ محدود). وDevOps تمدّ أجايل إلى التشغيل عبر الأتمتة — CI يبني ويختبر كلّ تغيير، وCD يُصدره.
Waterfall
Sequential, onceتسلسلي، مرّة واحدة

Each phase finished before the next. Best when requirements are stable and clear.تُكمَل كل مرحلة قبل التالية. الأنسب حين تكون المتطلبات ثابتة وواضحة.

Iterative

Agile

CI/CD unites dev and operations; automated testing and version control become essential.يوحّد CI/CD التطوير والتشغيل؛ ويصبح الاختبار الآلي والتحكم في الإصدارات لا غنى عنهما.

§5 · Version control with Git§5 · التحكم في الإصدارات بـ Git

A complete, browsable history of every change — an undo button for your whole project.تاريخٌ كامل قابل للتصفّح لكل تغيير — زرُّ تراجعٍ عن مشروعك كلِّه.

Git is the industry-standard distributed version-control system: every developer holds a full copy of the project history. It tracks your work in three areas — the working directory (your files), the staging area (changes marked for the next snapshot), and the repository (the committed history).

Git نظام التحكم في الإصدارات المعياري الموزّع: لدى كلّ مطوّرٍ نسخةٌ كاملة من تاريخ المشروع. ويتتبّع عملك في ثلاث مناطق — دليل العمل (ملفاتك)، ومنطقة التهيئة (التغييرات المُعلّمة للّقطة التالية)، والمستودع (التاريخ المحفوظ).

 
Working directory ──[ git add ]──▶ Staging area ──[ git commit ]──▶ Repository

git init                          # create a new repository
git add hello.py                  # stage a file for the next commit
git commit -m "Add hello script"  # save a snapshot with a message
git branch feature-login          # create a branch
git checkout feature-login        # switch to it
git merge feature-login           # combine it back into mainدليل العمل ──[ git add ]──▶ منطقة التهيئة ──[ git commit ]──▶ المستودع

git init                          # إنشاء مستودع جديد
git add hello.py                  # تهيئة ملف للّقطة التالية
git commit -m "Add hello script"  # حفظ لقطة مع رسالة
git branch feature-login          # إنشاء فرع
git checkout feature-login        # التبديل إليه
git merge feature-login           # دمجه في الفرع الرئيسي
🔀 Branch & mergeالتفريع والدمج: A branch is an independent line of development — experiment safely without disturbing working code, then merge it back. A merge conflict occurs when the same lines changed on both branches; Git marks it and asks you to resolve it. Remotes (GitHub, GitLab) host a shared copy: git push uploads, git pull downloads. الفرع خطُّ تطويرٍ مستقل — جرّب بأمانٍ دون الإخلال بالشيفرة العاملة، ثم ادمجه. ويحدث تعارض الدمج حين تُغيَّر الأسطر نفسُها في كلا الفرعين؛ فيُعلِّمه Git ويطلب منك حلَّه. وتستضيف المستودعات البعيدة (GitHub، GitLab) نسخةً مشتركة: git push يرفع، وgit pull ينزّل.

§1 · The Software Development Life Cycle

Software is not written in a single burst — it moves through six phases. Walk them, and watch the cost of a mistake climb.

The Software Development Life Cycle (SDLC) is a structured framework that describes what work is done, in what order, and how quality is controlled from the first idea to the retirement of a system. The classic form has six phases: requirements analysis, design, implementation, testing, deployment, and maintenance. 💡 What to notice A defect introduced in requirements but not caught until production costs roughly 100× more to fix than if it were caught at the start — that steep climb in the bar is the single strongest argument for testing early and often. And notice the last phase: maintenance is not a footnote — 60–80% of a product's total cost is spent here, after the first release. The life cycle is mostly what happens after "done".

§2 · From source code to a running program

The CPU runs only machine code. Watch a Java file compile once, then run anywhere on a virtual machine.

Human-written source code must be translated before a CPU can run it. There are three models. A compiler translates the whole file to machine code ahead of time (C, Go) — fast, but tied to one platform. An interpreter executes the source line by line at run time (the Python shell, JavaScript) — portable, but slower. The hybrid model compiles once to platform-independent bytecode, which a virtual machine (VM) then runs (Java, C#, Python). Press Step and trace one Java program from .java all the way to the CPU.

Trace: source → compile → bytecode → run

animated
💡 What to notice The compiler runs once, producing hello.class — the same bytecode file runs unchanged on Windows, macOS or Linux, because the VM is the part that differs per platform. That is what "compile once, run anywhere" means. Contrast an interpreter, which re-translates every line every time it runs, and a pure compiler (C), whose .exe is fast but locked to one OS+CPU. The bytecode+VM model trades a little speed for portability.
ModelTranslated whenPortabilitySpeedExample
CompiledOnce, before runLow (per platform)FastestC, Go
InterpretedEvery line, at run timeHighSlowestPython shell, JS
Bytecode + VMOnce to bytecode, VM at run timeHighMedium–HighJava, C#
⚙︎ The full build pipeline (compiled C): "Compilation" is really several stages: preprocess → compile → assemble → link → load → execute. Linking combines object files and pulls in library code (e.g. printf); loading is the OS placing the program in memory (Lecture 2's loader).

§3 · Testing & debugging

Testing shows a bug exists; debugging finds why. They are two different jobs.

Testing executes a program to find defects; debugging locates and fixes the cause of one that testing revealed. Testing is organised from the smallest unit of code up to the whole system.

⚖︎ Dijkstra's principle: "Testing can show the presence of bugs, but never their absence." Passing tests increases confidence; it never proves correctness.
Levels of testing
UnitOne function in isolation
IntegrationInteraction between modules
SystemThe whole integrated system
AcceptanceSystem vs. user requirements
Kinds of errors
SyntaxCompile time — missing bracket
RuntimeWhile running — divide by zero
LogicRuns, but wrong result
🐞 A systematic debugging process: 1. Reproduce the exact input → 2. Localise where it happens → 3. Understand the root cause → 4. Fix the cause, not the symptom → 5. Verify with the full regression suite. Logic errors are the hardest: the program does not crash, it simply gives the wrong answer.

§4 · Development methodologies

A methodology decides how the SDLC phases are arranged in time — once, in cycles, or continuously.

Waterfall runs the phases strictly in sequence — simple to manage, but a requirements mistake surfaces late and expensive. Iterative/Incremental builds the product in repeated cycles, each a small SDLC delivering a working increment. Agile (driven by the 2001 Manifesto) takes that further with short, adaptive cycles; its common frameworks are Scrum (fixed 2–4 week sprints) and Kanban (continuous flow, limited work-in-progress). DevOps extends Agile to operations through automation — CI builds and tests every change, CD releases it.

Waterfall
Sequential, once

Each phase finished before the next. Best when requirements are stable and clear.

Iterative
Repeated cycles

Working software early; requirements refined as understanding grows; risk spread out.

Agile
Scrum & Kanban

Short adaptive cycles. Working software over documentation; responding to change over a plan.

DevOps
Continuous, automated

CI/CD unites dev and operations; automated testing and version control become essential.

§5 · Version control with Git

A complete, browsable history of every change — an undo button for your whole project.

Git is the industry-standard distributed version-control system: every developer holds a full copy of the project history. It tracks your work in three areas — the working directory (your files), the staging area (changes marked for the next snapshot), and the repository (the committed history).

Working directory ──[ git add ]──▶ Staging area ──[ git commit ]──▶ Repository

git init                          # create a new repository
git add hello.py                  # stage a file for the next commit
git commit -m "Add hello script"  # save a snapshot with a message
git branch feature-login          # create a branch
git checkout feature-login        # switch to it
git merge feature-login           # combine it back into main
🔀 Branch & merge: A branch is an independent line of development — experiment safely without disturbing working code, then merge it back. A merge conflict occurs when the same lines changed on both branches; Git marks it and asks you to resolve it. Remotes (GitHub, GitLab) host a shared copy: git push uploads, git pull downloads.
